# 통합 후 판단

**하나의 API로 유지할 구조는 마련했지만, 보편적으로 성능만 좋아지는 교체품은 아직 아니다.** 공개 ZeroList 내부로 네이티브 풀을 옮겼고 상태·스크롤·데이터 변경을 검증했다. 지원하는 고정 높이만 풀을 쓰며, 동적 높이와 나머지 기능은 기존 구현으로 처리한다.

## 이번 측정에서 얻은 것

RN 0.87.1, 10만 건, Android/iOS Release에서 5개 리스트를 가벼운 셀과 무거운 셀로 비교했다. 비용 60회와 별도 화면 검사 20회, 총 80회의 유효 결과다. 평균과 범위는 [전체 표](README.md), 원본은 raw.zip에 있다.

| 조건                          | 통합 ZeroList |   FlatList | 판단             |
| ----------------------------- | ------------: | ---------: | ---------------- |
| Android 가벼운 셀 CPU         |        14.86% |     13.85% | 우위 없음        |
| Android 무거운 셀 CPU         |        35.13% |     24.74% | 약 42% 더 사용   |
| Android 무거운 셀 지연 프레임 |         5.37% |      1.16% | 4.21%p 높음      |
| iOS 가벼운 셀 CPU             |        16.98% |     21.51% | 약 21% 적게 사용 |
| iOS 무거운 셀 CPU             |        16.86% |     24.62% | 약 32% 적게 사용 |
| iOS 무거운 셀 메모리          |    462.38 MiB | 470.30 MiB | 약 1.7% 적음     |

CPU 비율은 사용량이며 사용자 작업 완료 속도가 아니다. iOS 무거운 셀은 FlashList의 메모리가 더 적었고(454.17 MiB), 기존 ZigPool은 CPU와 메모리 모두 더 낮았다(13.75%, 412.45 MiB). Android 무거운 셀은 FlashList·LegendList보다 메모리는 적었으나 지연 비율이 더 높았다. 모든 지표에서 가장 좋다는 결론은 낼 수 없다.

iOS의 지연 콜백은 모두 0%였지만 GPU 프레임이 전부 완벽했다는 뜻은 아니다. 통합 ZeroList의 가벼운 셀 화면 검사에서 평균 공백 0.049%, 순간 최대 23.23%, 최장 16.67ms가 있었다. 각 화면 검사는 1회다. 제목 오류와 겹침은 전체 20회에서 0이었다.

## 기존 ZigPool보다 비용이 늘어날 수 있는 이유

기존 실험은 슬롯의 React 트리까지 재사용했다. 통합판은 일반 renderItem 안의 useState가 다른 항목으로 넘어가지 않도록 내부 트리에 항목 key를 부여했다. 무거운 셀의 측정 구간에서 기존 ZigPool은 mount/unmount 0회였지만, 통합판은 Android 평균 48회씩, iOS 평균 153회씩이었다. 이 작업량 차이는 실제로 확인했다.

다만 이것만으로 Android 지연 증가의 원인을 확정할 수는 없다. 스크롤바 기본값, 콜백 지원, 상태 보호 등 제품의 동작도 다르고, 호스트 외부 부하와 실행별 편차도 있다. 이번에는 동일 바이너리 안의 이전 ZeroList를 별도 항목으로 두지 않았으므로 기존 ZeroList 대비 전후 개선율도 산출하지 않는다.

## 다음 개선의 우선순위

1. Android 무거운 셀에서 React 커밋·네이티브 자식 변경·배치·그리기 시간을 각각 추적하고, 한 가지 변경씩 같은 조건으로 비교한다. 상태 보호를 빼서 얻는 속도를 일반 API의 개선으로 취급하지 않는다.
2. 고정/동적 경로 전환 시 위치와 상태, 헤더 좌표·앵커 등 기존 호환성의 빈틈을 좁힌다. 현재는 전환 시 트리가 다시 생성될 수 있다.
3. 실물 저사양 Android와 iOS에서 시작 시간·준비 중 최대 메모리·긴 스크롤·빈번한 데이터 교체를 측정한다. 현재 표의 안정 구간 메모리로 최대 사용량을 주장하지 않는다.

현재 판단은 **통합 구조를 유지하면서 개선할 가치는 있으나, 양 플랫폼의 범용 기본 리스트로 바로 권할 근거는 부족하다**는 것이다. iOS CPU 결과는 유망하지만 Android 무거운 셀 회귀와 호환성 범위를 먼저 해결해야 한다.

## 실행의 투명성

기본 스크롤바 수정 전의 별도 실행은 보존하고 최종 표에 섞지 않았다. 최종 실행 중 LegendList 시작 로그 확인 실패로 비용 측정 전에 중단한 시도도 기록했다. 완료한 26회를 유지한 채 재개해 최종 유효 80회를 모았으며, 느린 실행도 포함했다. [실행 기록](runner-events.json) · [최종 실행 로그](runner.log).
