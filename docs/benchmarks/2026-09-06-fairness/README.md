# FlatList 비교 공정성 점검

**현재 벤치마크에는 우리 고정 템플릿 PoC에 유리한 조건이 있다. 범용 리스트 엔진의 우위를 증명한 비교로 해석하면 안 된다.** 수치 조작을 발견했다는 뜻이 아니라, 기능·셀 구조·부하·준비 정책을 같은 수준으로 통제하지 못했다는 뜻이다.

이번 작업은 코드와 기존 원자료의 재검토다. 기기 성능을 새로 측정하지 않았다. 수치는 같은 소스 `864b6e6` 바이너리의 [장식 통합 8종 비교](../2026-09-06-palette/README.md)에서만 가져왔다. 이후 명령 경로 138회 비교에는 FlatList가 없으므로 두 자료로 새 순위를 만들지 않는다. 점검 시점 소스는 `87ced2a`이며 FlatList·공통 셀·데이터·Solo·공통 검사 코드는 8종 측정 소스 이후 변경되지 않았다.

## 구조부터 다르다

| 항목 | FlatList | 현재 장식 통합 워클릿 PoC |
|---|---|---|
| 셀 갱신 | React 셀 렌더와 RN 텍스트 | 최초 고정 템플릿 생성 후 UI 워클릿으로 전용 텍스트 값 변경 |
| 지원 범위 | 이번 예제도 공통 React 셀 경로 사용 | 코드에서 고정 높이 simple/heavy만 허용 |
| 장식 | 기본은 RN View 64개 | 네이티브 장식 뷰 하나에서 64칸 그리기 |
| 데이터 | 공통 JS items 배열 | 같은 JS 배열 + UI 런타임 전체 사본 |
| 재사용 | 보이는 범위 변화에 따라 React 셀 생성·제거 | 14개 고정 슬롯에 다른 항목 연결 |

출력 값이 같아도 같은 RN 컴포넌트·같은 기능을 제공하는 것은 아니다. 전용 UILabel/TextView와 고정 텍스트 영역은 일반 RN Text의 모든 기능을 구현하지 않는다. 임의 자식·동적 높이·개별 장식의 터치 및 접근성·데이터 변경을 동일하게 지원한다고 검증하지 않았다. 단순화 비용을 포함한 **제품 구조 간 비교**이며 순수 리스트 알고리즘 비교가 아니다.

## 같은 장식 최적화를 FlatList에도 주면

| 지표 | Android 통합 FlatList | Android 우리 PoC | iOS 통합 FlatList | iOS 우리 PoC |
|---|---:|---:|---:|---:|
| 첫 제목·배치 중앙값 ms | 278.4 | 294.1 | 272.4 | 320.3 |
| 평상시 메모리 평균 MiB | 128.5 | 201.4 | 349.3 | 435.7 |
| 평상시 CPU 평균 % | 16.1 | 10.4 | 21.0 | 15.1 |
| JS 점유 평균 공백 % | 0 | 0 | 2.196 | 0 |
| JS 점유 지연 평균 % | 1.50 | 1.57 | 0 | 0 |

각 수치는 3회 결과다. 메모리는 Android PSS·iOS RSS이고, 지연은 각각 gfxinfo·CADisplayLink 콜백이다. 공백과 비용은 별도 실행이다.

동일 장식 최적화를 적용한 FlatList보다 **우리 메모리가 Android 약 57%, iOS 약 25% 더 높다.** 시작도 이 표에서는 FlatList가 앞선다. 우리에게 남는 관측상 이점은 평상시 CPU 사용률과 iOS 강한 JS 점유 조건의 공백이다. CPU 사용률이 낮다는 것이 같은 비율의 처리 속도 향상을 뜻하지 않는다. 이 대조군도 텍스트는 공통 RN Text를 쓰므로 완전한 동일 셀 비교는 아니다.

## 유리한 조건과 해석 제한

### 1. 고정 템플릿에 맞춘 시험 범위 — 중요

최근 전체 비교는 고정 높이 heavy 한 종류다. 셀당 4,000회 제곱근 계산과 64개 장식은 셀 재생성 비용을 크게 드러낸다. 계산을 다른 스레드로 옮긴 이점은 실제 구조적 차이지만, 일반 앱에서 같은 계산을 렌더마다 반복해야 하는지는 별개다. FlatList에도 결과 캐시·셀 단순화·작업 분산을 적용한 비교가 필요하다. 동일 최적화를 FlashList·LegendList에 적용한 최근 대조군도 없다.

이미지는 같은 작은 8×8 데이터 URI이며 본문은 제한된 단어를 반복한다. 네트워크 이미지·대형 사진 디코딩·서로 다른 긴 텍스트·복잡한 상호작용을 대표하지 않는다. 10만 건을 메모리에 올렸지만 측정 스크롤이 10만 건 전체를 지나간 것도 아니다.

### 2. 강한 JS 점유를 주요 장점으로 사용 — 중요

`Solo.tsx`는 200ms 타이머마다 160ms busy-loop를 돌린다. 명목상 약 80% 점유이며 실제 여유는 스케줄링에 따라 달라진다. JS 의존성이 낮은 구조를 드러내는 스트레스 시험으로는 타당하지만 평소 사용을 대표하지 않는다. 현재 정상 CPU·메모리 시험은 있으나, 최근 8종의 공통 공백 검사는 이 강한 부하 조건만 있다. 부하 없음·중간 부하·짧은 간헐적 작업에서도 정확성과 공백을 비교해야 한다.

### 3. 같은 5행 목표가 동일 준비 조건은 아니다 — 중요

FlatList 어댑터는 `windowSize = 1 + 2 × bufferRows × rowHeight / viewportHeight`로 지정한다. RN 0.87.1 설치 소스의 기본 windowSize는 21이므로, 이번 시험은 기본 설정 그대로의 FlatList 비교가 아니다. 첫 화면만큼의 initialNumToRender와 getItemLayout은 제공하지만, maxToRenderPerBatch와 updateCellsBatchingPeriod는 각각 설치 기본값 10·50ms에 맡긴다. 명시한 창 크기와 배치 정책의 여러 조합을 최근 동일 바이너리에서 비교하지 않았다.

작은 창은 FlatList 메모리를 줄이고 공백에는 불리할 수 있다. 따라서 단순히 모든 조건이 우리에게만 유리하다고 할 수도 없다. 동일 메모리 예산에서의 공백, 동일 공백 목표에서의 메모리로 각각 비교할 필요가 있다.

또한 removeClippedSubviews가 켜져 있으므로 **붙은 행 5~6개를 준비된 행 5~6개로 읽으면 안 된다.** 화면 밖 네이티브 뷰가 분리될 수 있다. React 셀·네이티브 뷰·표시 가능한 내용의 수는 따로 계측해야 한다. 고정 풀 14개와 붙은 행 수만 맞추는 것은 불충분하다.

### 4. 준비 비용 일부는 스크롤 점수 밖에 있다

스크롤 비용은 앱 시작 후 대기·준비 스와이프 12회·추가 2초 대기 이후 잰다. UI 전체 데이터 복사·JSON 복원은 이미 끝난 상태다. 그 비용은 준비 시간·최대 메모리까지 포함해서 평가해야 한다. 기존 첫 제목·배치 확인은 첫 화면이 맞다는 뜻이며 전체 UI 데이터가 준비됐다는 뜻이 아니다. 예컨대 우리 PoC의 첫 화면은 Android 294.1ms지만 UI 전체 데이터 준비는 별도 471ms였다. 공통 루트는 고정 높이에서도 모든 엔진에 offsets 배열을 생성하므로 각 라이브러리 최소 앱의 시작 비용 비교도 아니다.

### 5. 입력·계측이 모든 의미에서 동일하지 않다

같은 스와이프에도 실제 거리·속도는 다르다. 화면 검사에서 iOS 통합 FlatList는 평균 132.3행, 우리 PoC는 126.4행 이동했다. 약 4.5% 적은 이동이 우리 공백 결과를 유리하게 만들 가능성이 있으나 효과 크기는 미확정이다. Android는 각각 45.4·45.5행으로 비슷했다. 비용 실행은 별도이므로 이 거리 차이로 CPU 차이를 보정할 수 없으며, 비용 실행의 거리당 비용은 아직 산출하지 않았다.

공백 검사는 제목·행 좌표 중심이다. iOS RN 텍스트는 accessibilityLabel, 전용 뷰는 실제 UILabel 문자열을 읽는 경로도 있어 실제 픽셀 표시까지 동일하게 검증한 것이 아니다. 제목이 맞아도 본문·합계·색이 이전 값일 가능성은 이 검사만으로 배제할 수 없다. 별도 캡처 검사는 일부 화면에서만 이를 보완한다.

`inst` 카운터는 부모 효과에서 초기화되고 워클릿 계산은 render 콜백으로 세지 않는다. 0 renders/mounts를 초기 생성·전체 계산이 0이라는 증거로 쓰면 안 된다. FlatList에는 16ms 간격의 JS 스크롤 계측 콜백도 있다. 추가 계측 콜백의 비용과 FlatList 내부에서 필요한 스크롤 처리 비용을 구분해야 한다.

### 6. 범용 우위 주장에 부족한 반복·기기 범위

전체 8종은 각 조건 3회, 몇 초의 제스처다. 호스트 외부 부하를 통제하지 못했고 실제 기기·전력·발열·오래 사용한 메모리는 측정하지 않았다. 별도 정상 비용 측정과 공백 검사를 분리하고, 같은 바이너리·순서 섞기·원자료 보존을 한 것은 적절하다. 그것만으로 통계적 우위나 실물 재현까지 확보되는 것은 아니다.

## 정정한 결론과 다음 비교 기준

유지할 수 있는 결론은 **이 고정 화면에서 장식 통합과 UI 워클릿이 일부 CPU 비용 및 강한 JS 점유 시 공백을 줄였다**는 것이다. ‘FlatList보다 전반적으로 빠르고 메모리도 적다’, ‘동일 기능으로 우월하다’, ‘GPU 때문’이라는 결론은 근거가 부족하다.

다음 비교는 세 축을 분리해야 한다.

1. 일반 React 셀 비교: FlatList·ZeroList·FlashList·LegendList·기존 ZigPool을 동일 셀로 비교한다.
2. 템플릿 구조 비교: 동일 전용 텍스트·장식·계산 정책을 FlatList에도 적용해 워클릿·풀의 추가 효과를 분리한다.
3. 실제 도입 비교: 각 구현을 메모리·공백 목표에 맞춰 튜닝하고 실제 제품 데이터·변경·동적 높이·실물 기기로 평가한다.

어느 축에서든 정상·중간·강한 JS 부하, 첫 표시·상호작용 가능 시점, 준비 중 최대 메모리·정상 메모리, 같은 거리의 작업량, 내용 정확성을 함께 남겨야 한다. 이는 후속 측정 기준이며 이번 점검에서 이미 실행한 결과가 아니다.
