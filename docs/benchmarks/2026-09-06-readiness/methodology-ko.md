# 내용 준비 대기 개선 실험

RN 0.87.1, Release/Fabric/Hermes, 고정 높이의 무거운 셀 10만 건. 이전 독립 재측정과 동일한 준비 12회·측정 18회 스와이프, JS 160ms 점유/40ms 여유 조건이다. 앱을 매번 새로 실행하며 반대 플랫폼 앱은 종료한다. 이 작업이 실행한 빌드·녹화는 정량 측정과 겹치지 않는다. 다른 작업의 빌드·테스트까지 격리한 환경은 아니다.

## 비교 옵션

| 옵션 | 달라지는 부분 | 고정하는 부분 |
|---|---|---|
| 기존 고정 | 비교 기준 | 준비량·셀·렌더러 |
| 기존 범위 유지 | 기존 방향 예측과 준비 창 유지 | 준비량·셀·렌더러 |
| 우선순위 | 내용 교체 이벤트에 Discrete 우선순위 지정 | React 내용 생성, 커밋 매핑, 셀 개수 |
| 대기 보정 | 합쳐진 가장 오래된 요청부터 반영까지의 시간과 현재 미완료 요청 나이를 예측 예산에 포함 | 준비 공간 상한, React 내용 생성 |
| 우선순위+대기 보정 | 두 옵션을 함께 적용 | 같은 준비량 |

5행·12행은 보관 예산을 정하는 입력이다. iOS에서는 각각 총 14개·28개 슬롯이며, 선행 준비 옵션은 그 안에서 앞뒤 배분을 바꾼다. 실제로 언제나 양쪽에 5행씩 남기는 조건이라는 뜻은 아니다. 새 PoC 비교는 `bufferRows`를 명시한다.

대기 보정은 사라진 요청 하나하나의 처리 시간을 측정하는 방식이 아니다. 아직 충족하지 못한 준비 요청의 대기 구간을 보수적으로 반영한다. 방향이 바뀌어 필요 없어진 요청도 포함할 수 있으며, 시간 예산은 기존과 같은 500ms 상한이다. 슬롯을 추가하지 않는다.

## 실행 단계

1. iOS 단계 추적 4회: 기존 고정 5행, 우선순위 5행, 기존 범위 유지 12행, 대기 보정 12행. 로그가 추가되는 진단 실행으로, CPU·공백 순위에 합산하지 않는다.
2. iOS 탐색 18회: 9개 설정을 2회씩 비교. 기본 설정과 우선순위, 기존 범위 유지와 대기 보정, 조합을 5/12행에서 확인한다.
3. 별도 재검증: iOS 6개·Android 3개 설정에 일반 비용·JS 부하 공백·JS 부하 비용을 각각 3회 실행한다. 탐색 결과와 합쳐 중앙값을 내지 않는다. iOS는 기존 범위 유지 5행을 포함하여 대기 보정만의 차이를 구분한다.

우선순위는 일반 스크롤 이벤트 전체가 아니라 항목 매핑 교체 요청에만 적용한다. 실행 중인 JS 루프를 강제 중단하거나 UI 스레드를 JS 완료까지 기다리게 하는 동기 호출을 넣지 않았다. [Fabric 공식 설명](https://reactnative.dev/architecture/fabric-renderer)은 여러 우선순위의 이벤트 지원을 설명한다. 실제 사용 방식은 현재 설치된 RN 0.87.1의 `EventEmitter.h`, `RawEvent.h`, Android `Event.kt`를 확인했다. Android 이벤트 분류 상수는 Kotlin internal이므로 PoC에서는 RN 0.87.1의 Discrete 값 3을 명시했다. 이 경로는 버전 의존성을 가진 실험 옵션이며 기본값이 아니다.

## 단계 추적의 해석

네이티브 요청 → JS 수신 → React 렌더 시작 → 네이티브 props 반영 → 자식 내용까지 반영 후 배치를 같은 버전으로 연결한다. JS Date.now와 네이티브 벽시계를 사용하므로 약 1ms 반올림 차이가 있으며 -1ms도 원자료에 남긴다. React layout effect 시점은 추가 보조 로그이며 네이티브 반영 순서와 같다고 가정하지 않는다.

여러 요청이 하나의 React 커밋으로 합쳐지므로 요청 수신 표본과 실제 반영 표본 수가 다르다. 반영된 최신 요청만의 지연을 전체 요청 대기처럼 해석하지 않는다. 1회 진단 분포는 병목 위치를 찾는 근거이며 반복 성능 비교를 대체하지 않는다.

## 비용·정확성

공백 검사와 비용 측정은 별도 실행한다. 최대 공백은 이동 중 검사 프레임의 순간 빈 면적 최댓값, 최대 지속은 첫 공백 관측부터 해소 관측까지의 시간이다. 평균 공백은 이동 프레임의 빈 면적 평균을 실행별 계산한 뒤 중앙값을 취한다. 지속시간과 무공백 횟수는 정지 구간도 포함한다. 종료 PSS(Android)/RSS(iOS)는 피크가 아니다. iOS p95는 CADisplayLink 콜백 간격이며 실제 표시 프레임 지연과 같지 않다.

실물 저사양 기기, 동적 높이, 이미지 다운로드, 긴 실행의 발열·배터리는 이 실험의 검증 범위에 포함되지 않는다. 모든 비교 설정에서 동일한 보관 행 수가 동일한 메모리 사용량을 뜻하지 않는다.

## 로컬 재현

비교 옵션은 Solo 앱 실행 인자로 선택한다. 예를 들어 Android에서 같은 5행 예산으로 대기 보정을 켜려면 다음과 같이 실행한다.

```sh
adb shell am force-stop zerolist.example
adb shell am start -n zerolist.example/.SoloActivity --es engine zigpool --es preparation pending-stable --ei bufferRows 5 --ei count 100000 --es cell heavy
```

`preparation`을 `baseline`으로 바꾸면 기존 고정, `adaptive-stable`이면 기존 선행 준비다. `priority`는 우선순위 단독 실험이다. iOS는 같은 값을 `SIMCTL_CHILD_ZL_PREPARATION`으로 전달하고 `SIMCTL_CHILD_ZL_BUFFER_ROWS=5`를 명시한다. 화면 검사와 JS 부하를 켜는 전체 명령은 `record.py`에 보관했다.

재검증 전체는 `python3 -I docs/benchmarks/2026-09-06-readiness/run_confirmation.py`로 실행한다. 실행 경로가 이미 존재하면 원자료 보호를 위해 중단한다. 다른 디렉터리 이름으로 변경해야 하며, 기존 결과를 삭제하거나 덮어써서 재실행하지 않는다.

앱 빌드는 Android `:app:assembleRelease -PreactNativeArchitectures=arm64-v8a`, iOS `Release`, `iphonesimulator`, `ARCHS=arm64`로 수행했다. 새 빌드 CI는 추가하지 않았다.

## 호스트 경합으로 인한 해석 제한

Android 비용 측정 두 그룹에서 실행별 프레임 시간이 크게 달라져 호스트를 확인했다. 외부 Zig 테스트 하나의 시작 시각 01:15:19가 일반 비용 측정 01:15:12~01:16:58과 겹쳤으며 이후 부하 비용 구간에도 살아 있었다. 이후 관측에서는 여러 외부 테스트의 높은 CPU 사용량과 16개 논리 CPU 대비 높은 시스템 부하를 확인했다. 프레임 악화의 단독 원인으로 입증한 것은 아니다.

원자료를 삭제하지 않고 Android 비용 두 그룹을 통제된 성능 우위 판단에서 제외한다. `confirmation-summary.json`의 `cost_comparison_eligible`은 Android에서 false다. 외부 작업을 임의 종료하지 않았으며 호스트가 계속 바쁜 상태에서 추가 정량 재실행은 하지 않았다. iOS 측정 시간 전체의 호스트 모니터링도 없으므로 완전한 격리 실험으로 표현하지 않는다.

Android 우선순위 세 조합은 마지막에 각각 1회 동작 검사했다. 이 세 실행도 혼잡한 호스트에서 수행했으며 성능 순위에 사용하지 않는다.
