# Android가 느려 보인 원인과 현재 판단

**이전 수치만으로 통합 코드가 Android CPU를 42% 늘렸다고 단정할 수 없었다.** 같은 소스의 재측정 3회에서 ZeroList CPU 평균은 20.45%, 지연 1.10%였고, 같은 시점 FlatList는 23.31%, 0.69%였다. 이전 ZeroList의 35.13%, 5.37%가 재현되지 않았다.

당시 ZeroList 실행의 호스트 1분 부하는 약 28~38이었고 다수의 Zig 빌드·테스트가 함께 실행 중이었다. 수정 전 재측정은 약 3.6~4.9였다. [이전과 재측정의 호스트 기록](host-comparison.json). 외부 부하의 영향이 유력하지만 어느 프로세스가 지연 몇 프레임을 만들었는지 확정한 것은 아니다. 이전 수치를 삭제하거나 현재 수치와 빼서 코드 개선율로 계산하지 않는다.

## 시스템 추적에서 확인한 작업

무거운 셀의 별도 15초 추적에서 실제 스레드 실행 시간은 다음과 같았다. 스레드별 합계이며 비용 비교 점수와 섞지 않는다.

| 리스트              | UI 스레드 ms | JS 스레드 ms | 렌더링 스레드 ms |
| ------------------- | -----------: | -----------: | ---------------: |
| 통합 ZeroList       |       453.17 |       182.01 |           570.94 |
| FlatList            |       737.45 |       248.64 |           523.76 |
| 기존 ZigPool 어댑터 |       382.96 |       147.08 |           536.82 |

ZeroList의 셀 교체 46회에서는 RCTView 생성 2,990회와 RCTText 생성 138회가 관측됐다. 항목 key로 상태를 보호하기 위한 재생성이 실제 작업으로 존재한다. 그러나 이 실행에서 UI·JS 스레드 총시간이 FlatList보다 길지는 않았다. 가시 범위 계산·요청을 포함한 ZL.reposition 253회의 합계는 약 3.32ms였다. 큰 지연을 전부 이 계산 탓으로 설명할 근거도 없다.

[추적 분석](before-trace-analysis.json) · [JS 스레드를 포함한 실행 시간](before-running-threads.json) · [원본 추적](before-trace-raw.zip). 추적은 정상 수치와 별도 실행했고 gfx 범주는 켜지 않았다. 렌더링 스레드 시간도 GPU의 실제 실행 시간과 동일하지 않다.

## 변경 선택

부모 단위 스크롤과 Fabric 단독 배치는 중복 작업을 제거하고 큰 인덱스·터치·데이터 축소 검증을 통과했다. 후보 3회 비교에서는 CPU 22.85→19.23%, 재확인 5회에서는 20.92→20.45%였다. 그러나 마지막 5개 리스트 비교에서는 수정 전 20.59%, 수정 후 21.25%로 방향이 바뀌었다. 재확인 5쌍의 차이 구간도 0을 포함한다. [5쌍 차이](confirm-paired.json). 이 자료로 뚜렷한 속도 향상을 주장하지 않는다.

React 슬롯 memo는 짧은 실행의 평균만 좋아 보였으며 긴 실행에서 불리했다. 원인을 메모리 누수나 memo 자체 하나로 확정하지는 않지만, 이점이 유지되지 않은 후보를 기본값에 넣을 근거는 부족해 회수했다. React 상태 보호를 제거하거나 준비 메모리를 늘려 점수를 얻는 변경은 하지 않았다.

현재 남은 핵심은 실물 Android에서의 지속 스크롤·프레임 완료 추적과 항목 교체 비용이다. 현재 수치에서는 ZeroList의 CPU가 FlatList보다 낮은 조건도 있으나 무거운 셀의 지연·메모리는 더 높다. Android 우선으로 추가 개선할 대상이 남았으며 범용 교체 권장 단계라고 결론 내리지 않는다.
