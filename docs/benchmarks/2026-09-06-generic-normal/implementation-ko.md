# 동적 항목의 키·측정·상태 개선

이번 범용 ZeroList 수정은 **단일 열에서 측정 높이와 React 상태가 위치 번호가 아닌 항목의 고유 키를 따라가게 하는 것**이다. 기존 데이터 사본·준비 행 수·그리기 API를 바꾸지 않았다.

## 재현한 문제와 수정

기존 측정 캐시는 index→높이였다. 예를 들어 A의 높이가 300이고 B가 100일 때 순서를 B,A로 바꾸면 B에 A의 높이 300이 적용됐다. 앞 삽입과 삭제에서도 같은 문제가 있었다. 바깥 행의 React key도 index라서, 안쪽 항목 key가 같아도 다른 위치로 옮기면 로컬 상태가 초기화됐다.

- 측정 캐시를 항목 key→길이로 바꿨다. 데이터 갱신 시 현재 존재하는 키만 남겨 삭제된 항목의 기록을 회수한다. 항목 객체나 전체 데이터 사본을 캐시에 보관하지 않는다.
- 같은 키의 기존 크기는 실제 새 onLayout이 올 때까지 유지한다. 새 객체나 extraData라는 이유만으로 지우면, 실제 크기가 그대로여서 onLayout이 다시 오지 않을 때 유효한 측정을 잃기 때문이다.
- 단일 열의 바깥 React 행 key도 항목 key로 맞춰 재정렬 시 셀 상태가 항목을 따라가게 했다.
- 데이터 갱신 이전의 늦은 측정 콜백은 현재 커밋의 캐시와 다르면 무시한다. 중단된 React 렌더에서 현재 커밋의 캐시를 교체하지 않도록 커밋 단계에서 연결한다.
- 측정값이 없으면 데이터 전체를 훑지 않는다. 기존 측정 키를 모두 찾으면 보존 탐색을 일찍 끝낸다. 삭제된 키가 있으면 전체 데이터 탐색이 필요할 수 있다.

불변 데이터 배열과 항목을 구분하는 안정적인 키를 기준으로 검증했다. index 기반 키로 항목의 정체성을 구분할 수는 없다. 같은 키의 새 내용은 다음 실제 측정까지 이전 길이를 추정값으로 쓰므로 첫 반영 순간의 모든 레이아웃 이동을 없앴다는 뜻은 아니다.

## 수정 전후 검증

수정 전 코드에 회귀 검사를 적용하면 **재정렬·앞 삽입·삭제·셀 상태·오래된 onLayout의 5개 검사가 실패**했다. 수정 후에는 모두 통과했다. 추가로 같은 키의 객체 교체와 extraData, 새 실제 높이, 너비 변경 후 재측정, 삭제 캐시 회수·0 크기·10만 건의 불필요한 보존 탐색을 검사했다.

전체 **92개 테스트, 라이브러리 타입 검사, 린트**를 통과했다. [수정 전 실패 로그](회귀검사-수정전.txt) · [수정 후 통과 로그](회귀검사-수정후.txt). 앞선 renderItem 갱신 생략의 300→50회 검사도 유지한다. 이들은 React/순수 로직 검사이며 Android/iOS 실제 데이터 변경 화면을 검증한 것은 아니다.

## Android 증분 빌드 문제도 수정

라이브러리만 수정한 첫 Android 빌드가 createBundleReleaseJsAndAssets를 UP-TO-DATE로 판단했다. APK에서 새 함수가 빠진 것을 확인해 **성능 측정을 시작하기 전에 거부했다.** Metro가 모노레포 라이브러리 소스를 읽어도 Gradle의 기본 앱 입력 범위에는 포함되지 않은 것이 원인이었다.

예제 앱의 번들 작업 입력에 라이브러리 src와 package.json을 추가했다. 라이브러리 소스만 임시로 바꿔 `zerolistSource ... measurements.ts has changed`로 재번들되는 것을 확인한 뒤 원래 소스를 복원하고 최종 APK를 다시 만들었다. 최종 Android/iOS 번들 모두에서 새 측정 캐시와 항목 갱신 함수가 포함됨을 확인했다. [소스·실제 바이너리 해시](provenance.json) · [번들 입력 변경 검증 로그](번들입력-검증.txt).

소스 수정은 `407355f`, Android 로컬 빌드 입력 수정은 `ff2d985`다. Android/iOS 빌드 CI를 추가하지 않았다.

## 정상 부하 비교의 범위

이번 후속 비교는 FlatList·ZeroList·FlashList·LegendList·기존 ZigPool을 같은 새 Release 앱에서 실행한다. 공통 일반 React 셀을 쓰고, simple/heavy 각각 비용 3회·별도 화면 검사 1회씩 두 플랫폼에서 총 80회다. 강제 JS 점유는 없다. 기기는 Android 16/API 36 에뮬레이터와 iOS 26.2 iPhone 17 Pro 시뮬레이터이며 실물 검증이 아니다.

이 표는 **고정 높이의 정상 스크롤**이다. 동적 변경 중 기기 성능, 수정 전후 동일 바이너리의 속도 개선, 시작 비용·최대 메모리, 창·배치 정책 전체의 최적 성능을 입증하지 않는다. 이번 정확성 수정 때문에 프레임이나 메모리가 개선됐다고 직접 귀속하지 않는다. 공통 셀에서도 남는 비용과 정상 상태의 격차를 파악하는 자료다.

## 남은 범위

스크롤 중 앞 삽입·삭제의 화면 위치 유지, 다중 열의 동적 높이와 항목 이동 상태, 헤더·푸터·inverted를 포함한 전체 좌표 계약, 장시간 데이터 교체·실물 저사양 기기·전력은 별도 검증이 필요하다. 일반 RN renderItem의 JS 의존성도 사라지지 않았다. 범용 실투입이나 전체 라이브러리 우위를 선언하는 단계는 아니다.
