# 이번 개선의 판단

**범용 ZeroList의 동적 데이터 오류는 고쳤지만, 정상 부하의 성능 우위는 확인하지 못했다.** 이번 커밋을 채택할 이유는 키·측정·상태의 정확성과 새 코드가 실제 APK에 들어가는 빌드 신뢰성이다. 기존 renderItem 호출 감소를 앱 속도 향상으로 확대하지 않는다.

## ZeroList와 FlatList

동일한 새 RN 0.87.1 Release 앱, 10만 건, 강제 JS 점유 없음, 비용 각 3회 평균이다. CPU는 한 코어 기준 사용률이며 아래 상대 차이가 곧 속도 차이는 아니다.

| 환경                | ZeroList / FlatList CPU % | CPU 상대 차이 | 메모리 차이 MiB | ZeroList / FlatList 지연 % |
| ------------------- | ------------------------: | ------------: | --------------: | -------------------------: |
| android / 가벼운 셀 |             20.43 / 19.68 |         +3.8% |           -2.09 |                3.40 / 2.26 |
| android / 무거운 셀 |             31.79 / 27.55 |        +15.4% |           +2.20 |                2.96 / 1.53 |
| ios / 가벼운 셀     |             21.57 / 21.22 |         +1.7% |           -1.21 |                0.00 / 0.00 |
| ios / 무거운 셀     |             27.38 / 26.71 |         +2.5% |           -1.11 |                0.75 / 0.00 |

Android 지연은 gfxinfo 프레임이고 iOS는 CADisplayLink 콜백이다. iOS의 0%가 GPU 표시나 내용 준비까지 완벽하다는 뜻은 아니다. 범위는 [전체 5종 표](README.md)에 있으며 호스트 부하·이동량 차이 때문에 작은 평균 차이로 확정적인 순위를 정하지 않는다.

## 다른 경로에서 참고할 점

기존 ZigPool은 네 조건 모두 FlatList·ZeroList보다 CPU 평균이 낮았다. 특히 iOS 무거운 셀은 CPU 16.55%, 메모리 411.55MiB로 이번 표의 두 지표 평균이 가장 낮았다. Android 무거운 셀에서는 LegendList의 CPU·지연 평균이 더 낮은 대신 메모리가 더 컸다. FlashList도 Android 두 셀과 iOS 무거운 셀에서 ZeroList보다 CPU 평균이 낮았다.

코드와 측정 구간의 카운터에서 확인한 차이는 **셀 재사용**이다. ZeroList·FlatList는 창 이동 중 새 항목을 마운트하고 이전 항목을 제거한다. FlashList·LegendList·기존 ZigPool은 준비 이후 이번 측정 구간의 mount/unmount 증가가 0이었다. 그러나 FlatList와 ZeroList는 생성 횟수가 비슷한데도 비용이 달랐다. 이 카운터만으로 지연 원인 전체를 설명할 수 없으며, 재사용만 도입하면 같은 결과가 나온다는 인과 검증도 아니다.

## 정확성 및 내용 준비

별도 화면 검사 20회, 관측 8,059프레임에서 제목 오류·행 겹침은 0이었다. iOS 가벼운 셀의 ZeroList에는 평균 공백 면적 0.170%, 순간 최대 66.40%, 가장 긴 공백 구간 16.67ms가 관측됐다. 같은 조건의 FlatList·LegendList·ZigPool 공백 평균은 0, FlashList는 1.432%였다. 각 1회라 장시간 안정성 순위로 확대할 수 없다.

회귀 검사에서는 재정렬·앞 삽입·삭제·이동한 셀의 로컬 상태·오래된 onLayout 오류 5개를 수정 전 코드로 재현하고 수정 후 통과시켰다. 전체 92개 테스트가 통과했다. 화면 검사는 고정 높이이고, 동적 변경 검사는 React 테스트다. 둘을 합쳐 동적 데이터의 네이티브 시각 검증을 완료했다고 말하지 않는다.

## 다음 개선의 우선순위와 채택 기준

1. 일반 셀의 창 갱신·행 래퍼 갱신·마운트 비용을 따로 프로파일링한다. 재사용 경로를 넓히더라도 항목이 바뀔 때 로컬 상태가 다른 항목으로 새지 않는 계약을 먼저 검증한다.
2. 동적 높이의 측정 반영 시 전체 오프셋을 다시 만드는 비용과 앞 삽입·삭제 시 화면 위치 유지를 다룬다. 이번 고정 높이 비교는 이 비용을 측정하지 않았다.
3. 정상 부하뿐 아니라 빠른 방향 전환·데이터 교체·화면 크기 변경을 같은 공백·메모리 목표로 비교한다. 준비 행을 늘린 이득은 시작 시간과 최대 메모리 증가까지 같이 공개한다.
4. 실물 저사양 Android와 실물 iOS에서 반복한다. 현재 에뮬레이터·시뮬레이터 수치를 전력이나 구형 태블릿 체감으로 환산하지 않는다.

채택 기준은 정상 부하에서 경쟁 리스트 대비 CPU·지연·공백을 줄이면서 메모리와 데이터 변경 정확성을 악화시키지 않는 것이다. 일부 전용 경로의 우위는 다음 시도의 근거이며, 현재 범용 실투입을 확정하는 근거는 아니다.
