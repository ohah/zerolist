# Android 지연 프레임 원인 특정

제품 코드는 변경하지 않았다. 현재 APK에서 전체 프레임을 기록한 결과, **이번에 포착한 ZeroList 지연은 셀 배치·레이아웃보다 그래픽 명령 제출 이후 완료까지의 구간에 시간이 크게 걸렸다.** 다만 실제 GPU 연산, 드라이버, 에뮬레이터의 완료 통지 중 어느 내부 원인인지는 이 기록만으로 분리할 수 없다. 이를 실기기 GPU 병목으로 일반화하지 않는다.

## 이전 분석에서 빠졌던 것

`gfxinfo framestats`의 이전 기록은 마지막 120프레임만 남았다. ZeroList 전체 273프레임 중 지연 1건이 있었지만 마지막 120개에는 없었다. 전체 스레드 CPU 합계나 가장 긴 작업만으로 그 지연의 원인을 특정할 수 없었다.

이번에는 기존 FrameMetrics 리스너의 출력을 연속 저장하고, 각 지연 프레임의 의도된 VSync 시각으로 Perfetto의 실제 작업·스케줄러 상태를 대조했다. FrameTimeline의 `Unknown Jank` 표시는 지연 횟수로 사용하지 않았다.

## 조건과 수집 검증

- 코드 `2f9203d`, RN 0.87.1, Android 16 API 36 arm64 에뮬레이터, 1080×2400, Skia OpenGL (`skiagl`). 설치 APK 해시는 `provenance.json` 참조.
- 무거운 행 100,000개, bufferRows 5, 인위적 JS 점유 0ms. 워밍업 12회 뒤 측정 스와이프 18회.
- 현재 ZeroList, 같은 APK의 최적화 이전 네이티브 경로(`pool-baseline`), FlatList를 각각 FrameMetrics 단독 2회와 view/sched 추적 1회로 진단했다.
- 9회 모두 터치 down/up 합계 36개, FrameMetrics 콜백 누락 0, 첫 그리기 프레임 0. 전체 저장 프레임 수는 각 gfxinfo 합계와 일치한다. 3개 Perfetto 추적의 error/data_loss 통계는 비어 있다.
- 측정 시작부터 안정화까지 저장된 전체 프레임을 사용했다. FlatList는 마지막 터치 이후에도 추가 프레임이 있어 엔진별 분모가 다르다.
- 계측이 켜진 짧은 진단이다. 공식 성능 순위나 기존 비계측 벤치마크 대체 자료가 아니다. GPU 완료 측정에 영향을 줄 수 있는 `gfx` 추적 카테고리는 켜지 않았다.

| 경로 | FrameMetrics 단독 1회차 | 단독 2회차 | view/sched 추적 |
|---|---:|---:|---:|
| 현재 ZeroList | 1 / 272 | 2 / 273 | 1 / 272 |
| 이전 네이티브 경로 | 11 / 274 | 1 / 273 | 2 / 274 |
| FlatList | 6 / 289 | 4 / 289 | 3 / 290 |

표는 `TOTAL_DURATION > DEADLINE`인 횟수 / 전체 프레임 수다. 이전 경로 1회차만 gfxinfo의 지연 집계는 10건으로 FrameMetrics의 11건과 다르다. 두 정의를 억지로 맞추거나 해당 결과를 제거하지 않았다. 그 차이의 내부 집계 원인은 미확정이다. 나머지 8회는 일치한다. 이전 경로가 11→1로 변한 것만 보아도 이 결과로 개선율을 주장할 수 없다.

## 실제 지연 프레임 1: 제출은 빨랐고 완료가 늦었다

`frames-2-zero`, intended VSync `127029979769037`. 마지막 120프레임에도 포함되어 FrameMetrics와 gfxinfo의 절대 시각을 함께 확인할 수 있다.

| 단계 | 프레임 시작 이후 |
|---|---:|
| UI 입력 처리 시작 | 0.514ms |
| UI 그리기 준비 완료, 렌더 스레드에 전달 대기 시작 (`SyncQueued`) | 0.778ms |
| 렌더 스레드 동기화 시작 | 3.074ms |
| 그래픽 명령 제출 완료 | 4.507ms |
| 버퍼 교환 호출 완료 | 18.692ms |
| 시스템이 정한 마감 | 33.333ms |
| GPU 완료 및 전체 프레임 완료로 기록된 시각 | 33.683ms |

레이아웃은 **0.032ms**, UI 그리기 준비는 **0.023ms**였다. 그래픽 명령 제출 이후 GPU 완료 기록까지는 **29.176ms**다. 이 구간이 긴 상태에서 레이아웃의 작은 비용을 줄이는 것으로 큰 개선을 기대한 것이 문제였다.

FlatList의 `trace-flat`, intended `127093379766501`도 UI 준비 **0.677ms**, 제출 **3.247ms**, 버퍼 교환 완료 **18.815ms**, GPU 완료 **33.709ms**로 유사하다. 이 구간의 현상은 ZeroList에만 존재하지 않는다.

**주의:** GPU_DURATION은 명령 제출 완료에서 GPU 완료까지의 경과 시간이다. 실제 GPU 코어가 내내 연산했다는 뜻으로 사용하지 않는다. 버퍼 교환 구간과도 겹치므로 둘을 더하지 않는다. 이 자료는 화면에 실제 표시된 시각이나 입력부터 내용 표시까지의 지연을 직접 측정한 것이 아니다.

## 실제 지연 프레임 2: 셀 생성도 JS 점유도 없었다

`trace-zero`, intended `127065229767627`, 전체 **17.401ms**, 마감 **16.667ms**.

- 해당 프레임 구간에 겹치는 셀 생성·마운트 추적은 **0건**이었다.
- JS 스레드 `mqt_v_js` 실제 CPU 실행은 **0.129ms**, 메인 스레드는 **0.959ms**였다.
- `ZL.reposition`은 **0.006875ms**, 레이아웃 **0.051ms**, UI 그리기 준비 **0.083ms**였다.
- VSync 의도 시점부터 입력 처리 시작까지 **3.721ms**였다. 이 수치를 JS 실행 시간으로 해석하면 안 된다.
- RenderThread 실제 CPU 실행은 **8.541ms**, 비실행 상태 `S`는 **8.659ms**, 실행 가능 상태에서 CPU를 기다린 시간은 **0.200ms**였다.
- `DrawFrames`는 시작 후 **4.880ms**부터 **13.356ms**까지였고, FrameMetrics의 버퍼 교환 구간은 **6.594ms**였다. GPU 완료까지의 경과 시간은 **10.752ms**였다. 이 값들은 서로 겹치므로 합산하지 않는다.

메인 스레드의 `Choreographer#doFrame` 벽시계 시간도 **1.765ms**다. 셀 배치 함수나 JS가 이 프레임 전체를 붙잡은 현상이 아니다. 동시에 렌더 스레드 CPU 작업도 상당하므로 “GPU 대기만 문제”라고 단정하지 않는다.

현재 ZeroList 3회에서 잡힌 지연 4건 중 3건은 첫 측정 터치 후 약 31~37ms에 발생했고, 마감 초과는 각각 0.471 / 0.388 / 0.734ms였다. 나머지 1건이 위의 33.683ms 프레임으로 초과는 0.350ms였다. 프레임 시작 시점과 마감 여유도 영향을 준다. 항상 마감을 16.67ms로 고정하면 잘못 집계된다.

## 특정된 것과 남은 것

**특정된 경계:** 이번 현재 ZeroList 지연 표본에서는 UI 셀 배치·레이아웃의 비용이 작고, 렌더 스레드 작업·버퍼 교환·제출 이후 완료 구간이 더 길었다. 적어도 한 추적 지연 프레임은 셀 생성과 긴 JS 실행 없이 발생했다. 따라서 최근 레이아웃·좌표 갱신 변경이 지연 프레임을 크게 줄이지 못한 이유를 설명할 근거가 생겼다.

**아직 특정하지 못한 내부 원인:** 제출 이후 구간의 실제 GPU 연산량, 드라이버 내부 처리, 호스트/에뮬레이터의 완료 통지와 표시 주기 영향은 분리되지 않았다. 이 기록으로 과거 모든 실행의 원인이나 실기기 성능을 확정하지 않는다. 내용 준비 대기는 별도 지표이며, 이번 프레임 지연 분석으로 그 원인까지 해결했다고 주장하지 않는다.

다음 검증 우선순위는 동일 장면의 Android 실기기 프레임 추적이다. 그 결과에 따라 그래픽 작업량을 줄일지, 에뮬레이터에서만 나타나는 완료 지연을 별도로 취급할지 결정해야 한다. 지금은 추가 제품 최적화를 넣지 않았다.

## 재현 자료

- `record.py`, `trace.cfg`: 제품 수정 없이 9회 진단 수집. 새 출력 폴더가 필요하다.
- `analyze.py`: 전체 FrameMetrics 집계, gfxinfo 교차 확인, 지연 프레임 시각에 겹치는 스레드 상태·작업 추출. `INPUT` 및 `TRACE_PROCESSOR` 환경 변수로 경로 지정 가능.
- `analysis.json`: 프레임별 원시 지표, 추적 작업, 스레드 상태, gfxinfo 시각.
- `raw.zip`: 9회 로그·gfxinfo·호스트 상태와 3회 원본 추적 및 추출 작업 목록. ZIP을 별도 폴더에 풀어 분석 가능.

정의 근거: [Android FrameMetrics 문서](https://developer.android.com/reference/android/view/FrameMetrics), [Android 16 FrameMetrics.java의 DURATIONS 매핑](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/core/java/android/view/FrameMetrics.java).
