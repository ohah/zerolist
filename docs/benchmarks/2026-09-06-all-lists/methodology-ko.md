# 전체 리스트 비교 조건

이번 비교는 FlatList, ZeroList, FlashList, LegendList, 기존 ZigPool, 기존 UI 워클릿, 메모리 개선 UI 워클릿 **7종 전부를 같은 바이너리에서 새로 실행**한다. 과거 일부 엔진의 수치를 섞지 않는다.

## 환경과 범위

- RN 0.87.1 / FlashList 2.3.1 / LegendList 2.0.19 / Reanimated 4.6.0 / Worklets 0.12.1. 설치된 패키지에서 버전을 확인했다.
- ZeroList는 이 저장소의 `@ohah/zerolist` 구현이다. ZigPool은 별도 네이티브 풀 PoC다. 워클릿 두 버전도 고정 템플릿·전용 네이티브 텍스트를 사용하는 PoC이며 일반 리스트 API와 동등한 지원 범위가 아니다.
- Android 16 API 36 arm64 에뮬레이터, iOS 26.2 iPhone 17 Pro 시뮬레이터. 같은 네이티브 계측 커밋 `6dac750`의 arm64 Release. 원본과 APK·iOS 바이너리의 해시를 확인했다.
- 실제 데이터 10만 건, 고정 높이 무거운 셀. 제목·본문·이미지·64개 색상 뷰·4,000회 계산이 있다. 워클릿은 React 구조를 만든 뒤 UI에서 전용 텍스트와 색상을 바꾸므로 실행 경로는 다르다.
- GPU API나 리스트 구현은 이번 측정을 위해 변경하지 않았다. 한 번에 한 플랫폼의 측정 앱만 실행하고, 비용 측정 중 녹화·빌드를 하지 않는다.
- 모든 엔진을 포함하는 공통 측정 앱이다. 제품별 최소 번들을 별도로 만든 앱의 시작 시간을 비교한 것은 아니다.

## 준비량과 힌트

한쪽 화면 밖 준비 목표를 5행으로 맞추되 각 엔진의 API로 변환한다. **모든 엔진이 똑같은 수의 뷰를 만드는 것은 아니다.** 실제 붙어 있는 행 수를 별도로 보고한다.

| 엔진 | 준비 목표와 크기 힌트 |
|---|---|
| FlatList | `windowSize = 1 + 2×5×행높이/화면높이`, 첫 화면을 채우는 initialNumToRender, getItemLayout |
| ZeroList | 같은 windowSize·initialNumToRender·getItemLayout, estimatedItemSize |
| FlashList | drawDistance = 5×행높이, v2 자동 측정·재활용 |
| LegendList | drawDistance = 5×행높이, recycleItems, getFixedItemSize와 추정 크기 |
| ZigPool·워클릿 | overscan 5행, 화면 행 수 + 양쪽 여유의 고정 풀 |

FlatList·ZeroList는 첫 화면 행을 먼저 만들 수 있고, 풀 엔진은 풀 전체 구조를 만든다. 시작 시간 차이에는 초기 뷰 수와 런타임 초기화, 데이터 전달 경로의 차이가 포함된다. FlashList v2에 다른 리스트의 getItemLayout을 억지로 적용하지 않는다. 제품별 기본 설정이나 가능한 모든 튜닝을 비교한 것은 아니다.

## 측정 구간

1. **시작 42회:** 엔진·플랫폼별 3회. 별도 첫 1회씩 총 14회는 준비 실행으로 보존하고 통계에서 제외한다. 매번 프로세스를 종료하고 재실행하지만 OS/디스크 캐시는 지우지 않는다. 공통 순위는 네이티브 시작 진입부터 **현재 화면의 실제 제목·배치가 맞고 공백·겹침이 2px 이하인 첫 관측**까지다.
2. **평상시 비용 42회:** 인위적 JS 점유와 화면 검사를 끄고 CPU·메모리·지연을 측정한다.
3. **JS 점유 비용 42회:** JS를 160ms 점유하고 40ms 쉬는 부하에서 같은 비용을 측정한다.
4. **JS 점유 화면 검사 42회:** 비용 검사와 분리해 실제 네이티브 제목·좌표·공백·겹침을 읽는다.

총 정식 168회와 별도 시작 준비 14회다. 스크롤은 준비 스와이프 12회 후 동일한 정량 제스처 18회다. 각 회차는 저장된 난수 시드로 순서를 섞는다.

동일한 입력 제스처를 사용해도 실제 스크롤 이동 거리가 완전히 같지는 않다. 실행별 이동 행 수와 가시 영역 진입 준비율을 원자료·요약 JSON에 보존한다.

제스처 좌표·지속시간은 플랫폼 안에서 동일하게 고정한다. iOS와 Android 사이에서 같은 dp 이동량과 같은 감속 물리를 강제한 것은 아니므로 플랫폼별 공백 차이를 OS 자체의 우열로 해석하지 않는다.

CPU는 같은 입력을 처리하는 앱 전체의 평균 사용량이다. 행 하나당 비용이나 초당 처리 가능한 최대 행 수로 정규화한 지표가 아니므로 사용률 차이를 그대로 처리 속도 향상률로 바꾸지 않는다.

시작 시간의 Android 기준점은 SoloActivity onCreate, iOS는 AppDelegate didFinishLaunching 진입이다. OS 프로세스 생성 전부터의 앱 전체 시작 시간이 아니며 실제 GPU 제출 완료나 패널 표시 시각도 아니다. 본문·합계·색상의 전 프레임 검사는 하지 않는다.

워클릿의 UI 데이터 접근 가능 시점은 보조로만 표시한다. 일반 리스트에는 같은 의미의 별도 UI 데이터 사본이 없으므로 0ms로 채우거나 이 지표로 전체 순위를 매기지 않는다. 이전 워클릿 비교의 ‘데이터와 내용 모두 준비’ 시간과 이번 공통 시작 지표를 혼동하지 않는다.

## 해석의 제한

Android 메모리는 PSS, iOS는 RSS다. CPU는 한 코어 100% 기준 앱 프로세스 사용량이다. Android 지연은 gfxinfo의 지연 프레임, iOS는 CADisplayLink 지연 콜백이다. 플랫폼 간 같은 표시 누락률로 해석하지 않는다.

외부 호스트 작업을 통제하지 못하며 실행 전후 부하·프로세스 이름을 보존한다. 느린 실행을 제외하지 않는다. 각 3회 평균/중앙값과 범위를 함께 읽어야 하며 실물 구형 태블릿, 전력·발열, 동적 높이, 임의 React 자식, 데이터 변경·장시간 누수는 이번 검증 범위가 아니다.
