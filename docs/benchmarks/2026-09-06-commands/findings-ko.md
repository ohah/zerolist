# 판단: 명령 경로 변경만으로는 큰 개선이 없다

**기존 장식 통합을 기준으로 유지한다. 글자·장식 명령은 작은 개선 가능성을 확인하는 실험 옵션이며, 장식만 명령은 채택하지 않는다.** 같은 새 바이너리의 세 경로를 Android/iOS에서 정식 138회 비교한 결과다. 앞선 8종 리스트 순위를 새로 측정한 결과는 아니다.

## 무엇이 달라졌나

React가 만든 고정 템플릿을 재사용하는 구조에서, UI 워클릿이 글자·색을 바꾸는 방법만 변경했다. 기존 `useAnimatedProps`와 장식만 `dispatchCommand`, 글자·장식 모두 `dispatchCommand`를 비교했다. 14개 슬롯, 10만 건 데이터, 같은 글자·이미지·64칸 장식과 행 계산을 유지했다. GPU API 변경은 없다.

## 실제 이득은 작다

| 기존 → 글자·장식 명령    |          Android |              iOS |
| ------------------------ | ---------------: | ---------------: |
| 첫 제목·배치 확인 중앙값 |  296.5 → 285.2ms |  322.7 → 324.5ms |
| 평상시 메모리 평균       | 201.8 → 201.5MiB | 433.8 → 432.6MiB |
| 평상시 CPU 평균          |   12.08 → 11.53% |   15.24 → 14.99% |
| 평상시 지연 평균         |     1.59 → 1.17% |           0 → 0% |
| JS 점유 지연 평균        |     1.24 → 1.17% |           0 → 0% |

시작·평상시 비용은 각 5회, JS 점유 지연은 각 10회다. Android 메모리는 PSS, iOS는 RSS이고 지연 정의도 다르므로 OS끼리 순위를 매기지 않는다.

Android JS 점유에서 실제 지연 프레임 합계는 **34/2,738 → 32/2,738**이었다. 실행별 평균 차이는 **0.077%p**, 합계 차이는 두 프레임이다. 이 차이를 ‘압도적으로 빨라졌다’거나 안정적인 체감 개선으로 표현하지 않는다. 평상시 지연 평균은 줄었지만 기존 5회의 범위도 0.73~2.97%로 넓었다. 외부 호스트 부하를 통제하지 못했고 실물 재현도 없다.

장식만 명령은 Android JS 점유 지연이 1.24→1.42%로 늘었고, 평상시 메모리도 Android 201.8→203.2MiB, iOS 433.8→437.4MiB였다. 시작 시간의 소폭 차이만으로 이 경로를 채택할 이유는 부족하다.

## 왜 기대보다 차이가 작은가

이번 세 경로는 모두 이미 UI 워클릿으로 내용을 준비한다. 명령 버전만 새롭게 JS 스레드를 피하는 것이 아니다. 바꾼 것은 그 뒤의 값 전달 일부다.

[실제 설치 소스](code-paths-ko.md)에서 Android 명령은 RN의 명령 처리 큐에 들어감을 확인했다. 속성 갱신 일부를 줄여도 모든 반영 대기가 사라지는 구조가 아니다. iOS는 메인 큐에서 직접 실행할 수 있지만 측정상 큰 이득은 없었다. 데이터 보관·행 계산·배경색·배치·그리기·화면 합성 비용도 공통으로 남는다.

이는 **이번에 바꾼 구간이 큰 병목이 아닐 수 있다는 해석**을 지지한다. 큐 대기나 GPU가 전체 지연의 몇 %를 차지하는지 확정한 것은 아니다.

[별도 Android 시스템 추적](trace-findings-ko.md)에서는 글자·장식 명령의 긴 UI 프레임 48.40ms 중 CPU 실행 4.04ms, 잠든 상태의 대기 40.06ms를 관측했다. 명령으로 바꿔도 네이티브 그리기 쪽 대기는 남았다. 한 번의 진단이며 정상 반복 비교에 섞지 않는다. 기다린 대상이 GPU·드라이버 중 무엇인지는 아직 확정하지 않았다.

## 정확성과 채택 범위

화면 검사 18회·7,158프레임에서 관측한 제목 오류·겹침·공백은 모두 0이었다. 초기 화면의 장식 256개 중심 위치·색과 같은 행의 글자 픽셀도 일치했다. 풀 밖 실제 화면 20개 행의 제목·본문 접두부·합계와 장식 1,280개 색도 검사했다.

고정 템플릿 PoC의 일부 시나리오 검증이다. 모든 프레임의 전체 내용, 동적 높이, 임의 React 셀, 데이터 변경·삽입·삭제, 장시간 누수, 실물 저사양 기기는 미검증이다. 일반용 라이브러리로 도입할 근거까지 확보한 것은 아니다.

## 다음 우선순위

1. **실물 기기의 프레임 마감과 실제 표시 지연 확인.** 에뮬레이터에서 두 프레임 차이를 줄이는 것보다 체감 문제가 재현되는지 먼저 판단해야 한다.
2. **데이터의 중복 보관 비용 감소.** 현재 JS 데이터와 UI 데이터 사본이 함께 남는다. 공용 데이터 저장소나 제한된 범위 전달은 후보지만, JS 점유 중 내용 준비·업데이트 일관성을 함께 검증해야 한다. 이번에 구현·측정한 개선은 아니다.
3. **동적 높이와 데이터 변경의 정확성.** 템플릿 접근의 실제 사용 범위를 넓히는 검증이 필요하다. 명령 경로를 기본값으로 바꾸는 것은 후순위다.

원자료와 실행별 수치는 [전체 결과](README.md), 조건은 [측정 방법](methodology-ko.md)에 있다. 잘 나온 실행만 추리지 않았다.
