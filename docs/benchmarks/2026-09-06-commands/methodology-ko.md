# 네이티브 명령 경로 집중 비교

직전 실험은 장식 64개 뷰를 하나로 합쳐 시작·메모리·평상시 CPU를 줄였지만 Android JS 점유 지연이 남았다. 이번에는 **같은 장식 통합 화면의 갱신 경로만 세 가지로 나누어** 비교한다. 이전 8종 전체 수치를 새 결과에 섞지 않으며 이번 시험을 전체 라이브러리 순위로 제시하지 않는다.

## 세 경로

| 식별자                   | 화면 갱신 방식                                                   |
| ------------------------ | ---------------------------------------------------------------- |
| template-palette         | 직전 장식 통합 방식. 텍스트와 장식 색을 useAnimatedProps로 갱신  |
| template-palette-command | 텍스트는 기존 방식, 장식 색만 UI 워클릿의 dispatchCommand로 갱신 |
| template-command         | 텍스트 3개와 장식 색을 UI 워클릿의 dispatchCommand로 갱신        |

배경색과 풀 배치는 세 경로 모두 기존 방식을 사용한다. ‘명령’은 모든 RN 렌더링을 우회한다는 뜻이 아니다. 같은 네이티브 TextView/UILabel과 장식 뷰를 쓰며 텍스트·이미지·64칸·4,000회 제곱근 계산·10만 건 데이터·14개 슬롯을 유지한다. GPU API, 준비 행 수, JSON 데이터 전달 방식은 바꾸지 않았다.

명령 버전은 useAnimatedRef 연결도 추적하여 마운트 전에 최초 갱신을 보내고 잃지 않게 한다. iOS의 명령 값을 무관한 스타일 갱신이 초기 props 값으로 되돌리지 않도록, 문자열/색상 props 자체가 바뀌었을 때만 다시 적용한다. 이 가드는 동일 바이너리의 기준 경로에도 적용된다. 데이터 변경과 props/명령의 혼용은 일반 API로 검증하지 않았다.

[설치 소스의 호출 경로](code-paths-ko.md)도 확인했다. Android 명령은 RN 큐에 들어가므로 모든 반영 대기가 사라진다는 가정은 하지 않는다. iOS는 메인 큐에서 직접 명령을 실행할 수 있어 두 플랫폼의 경로가 다르다.

RN 0.87.1, Reanimated 4.6.0, Worklets 0.12.1, 소스 `ba8b86f`의 Android/iOS arm64 Release를 새로 빌드했다. Android 16 API 36 에뮬레이터와 iOS 26.2 iPhone 17 Pro 시뮬레이터다. [소스·바이너리 해시](provenance.json).

## 반복 수와 조건

- 시작: 플랫폼·경로별 5회, 총 30회. 별도 첫 1회씩 6회는 준비 실행으로 보존하고 제외한다.
- 평상시 비용: 플랫폼·경로별 5회, 총 30회.
- JS 점유 비용: 플랫폼·경로별 10회, 총 60회. 지연 편차가 커 반복 수를 늘렸다.
- JS 점유 화면 검사: 플랫폼·경로별 3회, 총 18회.

정식 합계 **138회와 별도 시작 준비 6회**다. 시작은 네이티브 진입부터 첫 실제 제목·배치 확인까지이며 앱 전체 시작이나 실제 패널 표시 시간은 아니다. UI 전체 데이터 준비 시간은 보조 지표로 분리한다.

스크롤은 한쪽 5행 준비 목표, 준비 스와이프 12회 후 측정 스와이프 18회다. JS 점유 조건은 160ms 작업과 40ms 여유를 반복한다. 순서 시드 870611로 각 회차 순서를 섞는다. 측정 중 빌드·OCR·녹화를 하지 않고 다른 플랫폼의 측정 앱도 종료한다.

Android 메모리는 PSS, iOS는 RSS다. CPU는 한 코어 100% 기준 앱 프로세스 평균 사용률이며 최대 처리량이 아니다. Android 지연은 gfxinfo, iOS는 CADisplayLink 콜백이다. 같은 종류의 패널 표시 누락률로 비교하지 않는다. 화면 검사와 비용 검사는 별도 실행이다. 제스처는 플랫폼 안에서 같지만 실제 이동 거리와 두 OS의 스크롤 물리는 같지 않다.

외부 호스트 부하는 통제하지 못했다. 실행 전후 부하와 프로세스 이름을 보존하고 느린 실행을 제외하지 않는다. 평균뿐 아니라 범위와 실행별 수치를 함께 본다. 10회 반복도 실물 기기의 통제된 시험이나 전체 구간 시스템 추적을 대체하지 않는다.

## 실제 화면 검증

초기 화면은 기준 경로와 두 명령 경로의 장식 64칸 중심 위치·색을 두 플랫폼에서 비교했다. 제목·본문·합계 영역은 동일 행의 실제 어두운 글자 픽셀을 비교한다. 행 경계 반올림 ±1px 정렬만 허용하며 빈 배경 비율로 오차를 희석하지 않는다. [초기 색 검사](pixel-validation.json), [초기 글자 검사](text-pixel-validation.json).

재활용 검사는 **처음 14개 슬롯 밖까지 12회 빠르게 스크롤한 화면**을 사용한다. 실제 화면에서 OCR로 행 번호를 읽고 해당 데이터의 색상 64칸, 제목, 표시된 본문 접두부, 합계를 확인한다. OCR의 발음 기호와 점 없는 i만 정규화하며 임의의 문자열 차이를 허용하지 않는다. 잘린 상단 행은 제외하고 이미지마다 완전한 행 2개 이상을 검사한다. [OCR 원본](ocr-observations.json), [풀 밖 검사 결과](reuse-validation.json).

위 검사는 일부 실제 캡처의 정확성 검사다. 스크롤 중 모든 프레임의 모든 색·본문·합계를 검증한 것은 아니다. 별도 네이티브 화면 검사에서는 실제 제목·배치·공백·겹침을 읽는다. 동적 높이, 임의 React 자식, 데이터 변경, 실물 구형 기기, 장시간 누수와 전력·발열은 미검증이다.

## 재현

`OUT_ROOT=<새 경로> python3 -I docs/benchmarks/2026-09-06-commands/run.py`

화면 검사는 정량 측정과 분리해 `screens.py`, `check_pixels.py`, `check_text_pixels.py`를 실행한다. `ocr.swift`를 `/private/tmp/zerolist-command-ocr`로 컴파일한 다음 `check_reuse.py`로 풀 밖 화면을 확인한다.

정량 시험 종료 후 `trace.py`, `analyze_trace.py`로 Android 시스템 추적을 별도 수집한다. 앞선 실험에서 관측 경로를 바꿨던 `gfx` 범주는 제외하고 스케줄링·view·FrameTimeline을 사용한다. 경로별 한 번의 15초 진단이므로 10회 정상 비교에 섞지 않는다. 이것도 무계측과 같은 동작이라고 보장할 수 없으며 GPU 실행 시간 자체를 측정하지 않는다.

이어 `capture.py`, `make_videos.py`로 비교 영상을 만들고 `report.py <원자료 경로>`, `visualize.py`로 표와 한글 이미지를 만든다. 영상은 별도 실행을 1배속으로 나란히 놓은 것으로 정량 점수나 동일 프레임의 직접 비교가 아니다.

라이브러리 타입 검사와 76개 테스트, 린트, 웹 빌드를 통과했다. 예제 전체의 별도 타입 검사는 기존 RN private Codegen import, LegendList ref와 util 오류가 남아 있어 통과했다고 주장하지 않는다. 새 엔진의 웹 등록 누락은 함께 보완했다.

변경 소스의 기존 CI 6개도 모두 통과했다. [CI 결과](source-ci.json). 빌드 CI를 새로 추가하지 않았다.
