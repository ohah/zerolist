# 실제 개발을 이어갈 가치가 있는가

**개발을 이어갈 근거는 있다. 범용 리스트를 대체할 제품으로 바로 도입할 근거는 아직 부족하다.**

판단 근거는 비슷한 메모리 구간에서의 CPU 비용과 JS 부하 시 공백이다. RN 0.85.0의 207회 측정에서는 Android ZigPool 고정 풀의 일반 스크롤 CPU가 FlatList보다 약 33% 낮았고, iOS 범위 유지 예측은 FlashList의 공백 억제 설정보다 약 35MiB 적은 종료 메모리를 사용했다. 프레임 시간 분포는 겹쳤다. 이는 RN 컴포넌트의 셀 재사용·갱신·준비 경로를 더 개발할 근거이며 GPU API의 효과를 입증한 결과는 아니다. 최신 RN 0.87.1에서는 iOS 예측 설정도 3회 중 1회 공백이 관측됐다. 그 실행의 평균 공백은 약 0.25%, 순간 최대 공백은 약 47.4%로, FlashList 12행의 순간 최대 약 24.9%보다 컸다. 따라서 구버전의 3회 무공백 결과를 일반화하지 않는다. 최신 비용 수치는 [별도 재측정 보고서](README.md)를 따른다.

## 먼저 적용할 화면

고정 높이에 가깝고 셀이 무거우며, 스크롤 중 JS가 다른 작업도 처리해야 하는 화면이 첫 후보다. 하나의 실제 화면에서 기존 리스트와 교체 가능한 형태로 검증하고, 범용 API 확장은 그 결과를 보고 결정한다.

일반적인 가벼운 목록의 최고 속도, 모든 기기에서의 우위, 저사양 태블릿의 발열·배터리 개선은 지금 결과에서 주장하지 않는다. CPU 사용량 감소는 배터리 측정값이 아니다.

## 제품화 전에 해결할 부분

- 현재 ZigPool 예제 어댑터는 `fixedHeight`를 기준으로 배치하고 `useNoopScrollable`을 사용한다. 동적 높이와 `scrollToIndex` 같은 프로그램 스크롤까지 갖춘 대체재가 아니다.
- 이미지 로딩으로 인한 높이 변경, 데이터 추가·삭제, 빠른 역방향 스크롤, 화면 회전에서도 위치와 내용이 맞아야 한다.
- 접근성·포커스·터치·셀 내부 상태가 재사용 과정에서 다른 항목으로 넘어가지 않아야 한다.
- 저사양 Android 실기기와 실제 iPhone/iPad에서 메모리 압박, 긴 스크롤, GC, 실제 표시 프레임을 확인해야 한다. 현재 종료 메모리 샘플은 최고 사용량이나 메모리 상한이 아니다. 테스트 APK도 arm64 전용이므로 32비트 구형 기기 지원을 검증한 것은 아니다.

## 다음 투자 판단

최신 RN에서도 이점이 유지되고, 실제 화면에서 같은 공백 수준을 더 적은 비용으로 달성하며, 위 기능의 정확성을 지킬 수 있으면 시범 도입할 가치가 있다. 반대로 기능을 갖추면서 이점이 사라지거나 공백을 없애기 위해 과도한 메모리가 필요해진다면 기존 리스트를 조정해서 사용하는 편이 낫다.

현재의 권고는 **성능 PoC를 실제 화면 검증으로 발전시키는 것**이다. 전체 앱의 리스트를 바로 교체하거나 GPU 구현을 더 복잡하게 만드는 것은 이번 측정만으로 정당화되지 않는다.
