# 자원 예산 비교 방법

질문은 두 가지다. 비슷한 앱 종료 메모리 구간에서 어느 목록이 공백을 덜 만드는가? 같은 공백 수준을 만족하는 데 어느 목록이 메모리와 작업량을 덜 쓰는가? 지연 프레임 비율을 실행 속도의 배수로 바꾸지 않는다.

## 같은 입력과 데이터

React Native 0.85.0, FlashList 2.3.1, LegendList 2.0.19를 사용한다. 각 플랫폼의 모든 설정을 같은 Release 바이너리에서 실행한다. 10만 건의 고정 높이 복잡한 행은 동일한 텍스트·작은 데이터 URI 이미지·64개 하위 뷰·렌더 시 동기 연산을 포함한다. 데이터 생성과 RN 비용도 앱 메모리에 포함한다.

각 실행은 앱 프로세스를 새로 시작한다. 반대 플랫폼의 측정 앱도 종료한다. 최초 iOS 탐색에는 Android의 JS 점유 앱이 남아 있어 해당 그룹을 최종 비교에서 제외하고, Android 앱 종료를 확인한 isolated-ios 그룹으로 전부 다시 측정했다. 측정 드라이버도 종료 시 앱 정리를 수행하도록 보완했다. 빠른 스와이프 12회, 관성 중단 터치, 2초 대기로 시작 경계에서 벗어난 뒤 정상 3회·고속 6회·역방향 6회·정상 3회를 입력한다. OS별 제스처 좌표·물리·이동 거리는 다르므로 OS 수치끼리 우열을 비교하지 않는다. 같은 OS에서도 똑같은 입력이 이동 거리를 완전히 같게 만들지는 않으며, 검사 실행의 실제 이동 행 수를 원자료에 남긴다.

JS 부하는 160ms 점유 뒤 40ms 여유를 반복한다. 모든 목록의 동일한 Solo 루트에서 실행한다. ZigPool 전용 bindingDelay 타이머는 사용하지 않는다. 측정 전 준비 이동부터 부하가 걸려 있으므로 갑작스러운 부하 변화나 일반 앱의 평균 부하를 대표하지 않는다.

## 설정과 초기 보관량

한쪽 여유 2·5·12행을 기준으로 총 17개 설정을 탐색한다.

- FlatList/기존 ZeroList: `windowSize = 1 + 2 × 여유 행 수 × 행 높이 / 화면 높이`.
- FlashList/LegendList: `drawDistance = 여유 행 수 × 행 높이`.
- ZigPool 고정: `풀 크기 = ceil(화면 높이 / 행 높이) + 2 × 여유 행 수`, overscan은 지정 행 수.
- ZigPool 범위 유지 예측: 여유 5·12행의 같은 풀 용량에서 배분·유지 방식만 변경.

설정값은 공칭 여유다. 방향별 배분, 반올림, 재활용 보관과 초기 항목 유지 방식이 다르므로 실제 셀 수나 메모리가 같다는 뜻이 아니다. 최종 비교는 실제 종료 메모리 표본에 같은 예산 기준을 적용하며, 측정하지 않은 설정을 보간하지 않는다.

FlatList는 최초 렌더 항목을 유지하므로 초기 12행을 그대로 두면 작은 풀과의 비교에서 불필요한 보관량 차이가 난다. 예산 비교에서는 FlatList와 ZeroList의 `initialNumToRender`를 화면을 채우는 행 수의 올림으로 설정했다. FlatList/ZeroList에는 기존 getItemLayout을, LegendList에는 추정값에 더해 getFixedItemSize를 제공했다. FlashList v2의 크기 측정·재사용 경로는 유지했다. 비교 옵션이 없으면 각 어댑터의 기존 설정은 유지된다.

## 공백과 내용 검사

측정 옵션에서만 각 실제 Cell 루트에 행 번호를 담은 testID를 붙인다. 공통 네이티브 검사기는 모든 목록에서 이 루트의 실제 화면 좌표, 가시 영역, 제목 텍스트를 읽는다. Android는 배치가 끝난 OnDraw, iOS는 CADisplayLink에서 검사한다. JS가 바쁜 동안에도 관측할 수 있지만 실제 GPU 표시 완료 시각은 아니다.

주 지표는 스크롤 위치가 바뀐 관측 프레임의 평균 공백 면적 비율이다. 행 영역들의 합집합을 가시 영역에서 빼서 공백을 구하고, 물리 픽셀/포인트의 반올림 오차를 위해 2단위까지 허용한다. 공백이 있던 이동 프레임 비율과 최대 공백 면적도 함께 남긴다. 평균만 작고 잠깐 전체가 비는 경우를 숨기지 않는다.

공통 검사에 남긴 `entry_ready_percent`는 경계 반올림 때문에 실제 공백이 없는 경우에도 100% 미만일 수 있다. 이번 순위에는 사용하지 않는다. Android의 공칭 dp 행 높이를 정수 픽셀 높이로 오해하거나, 라이브러리의 실측 반올림을 오표시로 판단했던 초기 파일럿은 제외했다. 행 번호·제목·위치 불일치 및 겹침은 별도로 확인한다.

## 프레임·CPU·메모리

p95는 시간 분포의 95백분위, 즉 느린 상위 5% 경계다. 지연 비율과 p95가 모두 낮아야 한다는 단일 점수를 만들지 않고 각각 제시한다. CPU 비율은 모든 앱 스레드의 합이라 100%를 넘을 수 있다.

공백 검사와 별도로 commonAudit 및 준비 로그를 끄고 실행한다. 녹화와 시스템 상세 그래픽 추적도 끈다. Android 그래픽 API는 기존 OpenGL(skiagl)이며 변경하지 않는다.

- Android: gfxinfo의 지연 프레임 비율과 p95, 앱 종료 PSS 표본.
- iOS: CADisplayLink 시각 간격의 p95와 예산의 1.5배를 넘은 비율, 앱 종료 RSS 표본. 실제 표시 프레임의 지연률이 아니다.
- CPU: Android `/proc/PID/stat`의 user+system 시간, iOS `ps time`의 프로세스 누적 시간을 측정 구간 전후로 읽는다. 벽시계 시간으로 나눈 1코어 기준 비율이며 JS 강제 점유 자체를 포함한다. 전력·발열이나 배터리 소모를 직접 측정한 값이 아니다.
- 셀 렌더·생성·제거·콜백 횟수: 감사 실행에서 주기적 카운터 차이를 구한다. 관측 이동 행 수로 정규화한 렌더 횟수도 제공한다. CPU 시간과 동일한 지표가 아니다.

메모리는 시작·종료 표본이며 피크·GC 후 최소치가 아니다. 저사양 실물 기기, 동적 높이, 대형 이미지 디코딩, 초기 화면 완료 시간은 이번 범위에 포함하지 않는다. 따라서 결과는 이 부하와 환경의 조건부 판단이며 범용 제품 도입을 확정하지 않는다.
