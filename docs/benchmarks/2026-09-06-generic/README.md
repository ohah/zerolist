# 범용 경로의 첫 개선: 바뀐 항목만 renderItem 호출

**목표를 고정 템플릿의 특수 조건 최적화에서, 일반 React 셀을 쓰는 공개 ZeroList의 비용·정확성 개선으로 옮긴다.** 모든 조건에서 가장 빠르다고 보장하는 목표는 아니다. 지원 기능을 맞추고 정상 부하·메모리·초기 준비·변경 정확성을 함께 개선하는 방향이다.

## 이번에 구현한 부분

공개 `packages/zerolist/src/list.tsx`는 창이 한 행 움직일 때 창 안 모든 항목의 `renderItem`을 다시 호출했다. 호출 결과의 자식 컴포넌트가 별도 memo를 쓰더라도 renderItem 함수 본문과 element 생성은 실행됐다.

항목 내용에 memo 경계를 추가해 item·index·renderItem·separators·extraData가 같은 경우 호출을 생략한다. 바뀐 항목과 새로 진입한 항목은 갱신한다. `extraData`는 항목 외부 선택 상태 등의 갱신을 전달한다. API·일반 React 셀·데이터 사본 수·창 크기를 바꾸지 않았다. 네이티브 템플릿 전용 뷰도 요구하지 않는다.

FlatList 설치 소스의 CellRenderer도 PureComponent를 사용한다. 이번 수정은 FlatList보다 우월함을 증명한 것이 아니라 우리 범용 구현의 불필요한 호출을 줄인 것이다.

## 같은 React 테스트의 수정 전후

| 시나리오 | 수정 전 renderItem 호출 | 수정 후 |
|---|---:|---:|
| 10만 건, 높이 100, 뷰포트 500, 창 1배, 한 행씩 50번 이동 | 300 | 50 |
| 보이는 항목 3개 중 객체 하나 교체 | 3 | 1 |

첫 시나리오는 초기 렌더·뷰포트 설정 뒤 호출 수를 초기화한다. 경계 항목을 포함해 창에 6개가 있고 매번 1개가 새로 들어온다. 수정 전 새 동작을 기대하는 두 검사가 각각 300/3회로 실패함을 확인한 다음 구현을 바꿔 같은 검사를 통과시켰다. 50회 이동 후 실제 React 트리에서 50·55번 셀이 있고 49번이 없는지도 검사한다.

**React Native Jest 환경의 작업 횟수 검증이다. 기기 성능·CPU 시간·메모리·프레임을 새로 측정하지 않았으며 6배 빨라졌다는 뜻이 아니다.** 기존 heavy 벤치의 Cell은 이미 memo여서 실제 무거운 셀 계산의 감소 폭이 위 renderItem 호출 감소와 같지도 않다. 새 memo 컴포넌트의 비교·React 트리 비용도 있어 실제 기기 회귀 검사가 필요하다.

## 기능 검증

- extraData로 같은 항목 객체의 외부 선택 상태 변경
- 항목 객체 교체, 앞 삽입, 삭제, renderItem 교체와 index 표시
- 동적 높이 측정값을 반영한 창 계산
- 창에 남은 셀의 로컬 상태와 컨텍스트 갱신
- 기존 헤더·푸터·구분자·다중 열·스크롤·가시성 테스트

전체 **81개 테스트, 라이브러리 타입 검사, 린트**를 통과했다. 이번 동적 높이 검사는 재측정 후 창 계산 한 시나리오다. 높이가 다른 항목의 재정렬·삽입과 스크롤 위치 유지까지 모두 해결했다고 주장하지 않는다. 일반적인 불변 데이터 갱신을 전제로 하며, 객체를 제자리 변경할 때는 extraData 등 명시적인 무효화가 필요하다.

## 다음 개발과 채택 기준

1. **범용 기능의 정확성부터 닫는다.** 동적 높이, 삽입·삭제·재정렬, 키와 셀 상태, 화면 위치 유지, 접근성을 실제 화면에서 검증한다. 호출을 줄였어도 내용이 오래되거나 위치가 튀면 채택하지 않는다.
2. **일반 React 셀로 비교한다.** FlatList·FlashList·LegendList에 동일 셀·동일 최적화 기회를 주고 각 준비·배치 설정을 함께 탐색한다. 동일 메모리 예산의 공백과 동일 공백 목표의 메모리를 비교한다. 고정 14행만 기준으로 삼지 않는다.
3. **정상 부하를 우선한다.** 가벼운 셀·복잡한 셀, 정상·간헐·강한 JS 점유를 분리한다. 첫 표시·사용 가능 시점·준비 중 최대 메모리·안정 상태·장시간 상태를 함께 본다.
4. **스레드 이동은 지원 기능을 유지하며 선택한다.** 일반 React renderItem을 그대로 UI 워클릿으로 실행할 수 있다고 가정하지 않는다. 향후 네이티브 요청·준비 작업량 조절과 제한된 데이터 전달을 검토하되 전체 데이터 사본이나 거대한 미리 준비로 비용을 숨기지 않는다.
5. **실물 Android/iOS에서 효과를 확인한다.** 현재 시뮬레이터 결과만으로 실투입 권장을 바꾸지 않는다. 정상 화면의 작은 이득보다 다른 화면의 큰 회귀가 있으면 기본 경로에 채택하지 않는다.

이 목록은 후속 작업이며 이번 커밋에서 완료한 범위는 항목 갱신 생략과 관련 React 검증이다. 고정 템플릿 PoC를 동적 높이 범용 엔진으로 완성한 것은 아니다.
