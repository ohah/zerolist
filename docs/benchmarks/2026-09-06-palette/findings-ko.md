# 이번 시도의 판단

**시작·메모리·평상시 CPU를 줄이는 데는 효과가 있었다. Android JS 점유 시 지연 안정성은 해결하지 못했다.** 고정 템플릿 PoC의 개선으로는 유효하지만, 범용 리스트의 도입 근거나 실물 구형 기기의 성능 보장으로 확대하지 않는다.

## 직전 워클릿과 비교

동일한 새 Release 바이너리에서 10만 건 무거운 셀을 조건별 3회씩 측정했다. 시작은 첫 제목·배치 확인의 중앙값, 비용은 3회 평균이다.

| 지표 | iOS 직전 → 후보 | Android 직전 → 후보 |
|---|---:|---:|
| 첫 내용 확인 | 496.2 → 320.3ms, 35.5% 감소 | 498.7 → 294.1ms, 41.0% 감소 |
| UI 전체 데이터 접근 가능 | 682 → 458ms | 731 → 471ms |
| 평상시 메모리 | 517.3 → 435.7MiB, 15.8% 감소 | 284.2 → 201.4MiB, 29.1% 감소 |
| 평상시 CPU | 16.0 → 15.1% | 18.5 → 10.4% |
| 평상시 지연 비율 | 0 → 0% | 1.84 → 1.09% |
| JS 점유 시 지연 비율 | 0 → 0% | **0.85 → 1.57% 증가** |
| JS 점유 시 평균 공백 | 0 → 0%, 모두 3/3 무공백 | 0 → 0%, 모두 3/3 무공백 |

Android CPU 평균은 상대적으로 43.6% 낮았지만 이것을 처리 속도 43.6% 향상으로 읽으면 안 된다. 동일한 입력을 처리하는 앱 전체 사용률이며 최대 처리량이 아니다. 화면 검사에서 이동 행 수 평균은 Android 45.1 → 45.5, iOS 130.7 → 126.4로 완전히 같지 않았다. 비용과 화면 검사는 별도 실행이다.

Android 정식 JS 점유 검사에서 지연 프레임은 직전 7/820개, 후보 13/824개였다. 추가 6회에서 후보의 한 실행은 45/212개·21.23%까지 높아졌고, 다음 두 실행은 0.73%·1.09%였다. 큰 지연과 외부 빌드 34개가 동시에 관측됐지만 인과관계는 확정하지 못했다. **느린 실행도 모두 보존했으며 추가 결과를 정식 평균에 섞지 않았다.** [추가 검사와 최근 프레임 구간 분석](followup-ko.md).

## 무엇을 바꿨나

행마다 장식 64칸을 64개 애니메이션 뷰로 만들던 것을 **한 네이티브 뷰가 같은 64칸을 그리도록** 바꿨다. 풀 14행의 장식용 애니메이션 구독은 896개에서 14개가 됐다. 같은 칸 수와 색, 제목·본문·합계·이미지, 4,000회 계산, 10만 건 데이터, 준비 행 수를 유지했다.

관리할 뷰·레이아웃 노드·애니메이션 구독이 줄었다. 이는 이번에 바꾼 비용 구조다. 뷰 수 감소와 구독 수 감소 각각의 기여율을 별도 프로파일링으로 분해한 것은 아니다. Android Canvas와 iOS drawRect를 사용하며 GPU API 설정을 바꾸지 않았다. **GPU 종류를 바꿔 얻은 개선으로 주장하지 않는다.**

## FlatList 대조군이 보여주는 한계

같은 장식 통합을 일반 FlatList에도 적용했다. 리스트 알고리즘 이점과 셀 구조 개선 효과를 구분하기 위한 대조군이다.

| 지표 | iOS 통합 FlatList / 후보 | Android 통합 FlatList / 후보 |
|---|---:|---:|
| 첫 내용 확인 ms | 272.4 / 320.3 | 278.4 / 294.1 |
| 평상시 메모리 MiB | 349.3 / 435.7 | 128.5 / 201.4 |
| 평상시 CPU % | 21.0 / 15.1 | 16.1 / 10.4 |
| JS 점유 평균 공백 % | 2.196 / 0 | 0 / 0 |

장식 통합 FlatList는 두 플랫폼에서 더 적은 메모리를 쓰고 첫 내용을 더 빨리 확인했다. 후보의 차별점은 이번 **iOS JS 점유 조건의 무공백과 낮은 평상시 CPU**다. Android 공백은 8종 모두 0이어서 그 지표로 후보의 우위를 주장할 수 없다. 첫 화면에 붙은 행 수도 FlatList 4개와 워클릿 14개로 달랐다.

FlashList·LegendList·ZeroList에도 같은 셀 최적화가 도움이 될 수 있지만 이번에는 이들까지 장식 통합 버전을 만들지는 않았다. 따라서 후보와 원래 셀을 쓰는 경쟁 라이브러리의 차이를 전부 리스트 알고리즘의 우위로 해석하지 않는다. 8종 전체 수치와 범위는 [전체 보고서](README.md)에 있다.

## 검증과 남은 과제

- 정식 192회 + Android 지연 추가 6회. 별도 시작 준비 16회와 예비 시작 실행 16회도 원본을 보존했다.
- 스크롤 화면 검사 48회·19,145프레임에서 제목 오류·겹침은 0이었다. 워클릿 두 버전은 각 플랫폼 3회 모두 무공백이었다.
- 초기 비교 256칸과 스크롤 후 후보 384칸의 실제 중심 픽셀을 확인했다. 위치 차이 최대 1픽셀, 색상 차이 채널당 최대 1이었다. 모든 프레임의 모든 색·본문·합계를 검증한 것은 아니다.
- Android/iOS Release, 76개 테스트, 라이브러리 타입 검사, 린트, 웹 빌드, 소스 커밋의 기존 CI 6개가 통과했다. 새 빌드 CI는 추가하지 않았다.

남은 우선순위는 **지연 원인의 전체 구간 추적, UI 데이터 사본 등 추가 메모리 비용 축소, 실물 저사양 기기 검증**이다. 이번 후보는 전체 너비·고정 높이·전용 템플릿에 한정된다. 임의 React 셀, 동적 높이, 개별 장식의 터치·접근성, 데이터 변경과 장시간 누수까지 해결된 일반 라이브러리는 아니다.

제 판단은 **고정 템플릿 최적화 연구는 계속할 가치가 있지만, 현재 지연 결과로 범용 도입을 권하기는 이르다**는 것이다. 일반 화면에서는 셀 장식 통합만 적용하는 방법도 유효한 대안이다.
