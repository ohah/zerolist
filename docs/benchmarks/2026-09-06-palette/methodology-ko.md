# 장식 통합 후보 비교 조건

이번에는 **FlatList·ZeroList·FlashList·LegendList·기존 ZigPool·메모리 개선 워클릿·장식 통합 워클릿·장식 통합 FlatList** 8종을 같은 새 바이너리에서 측정한다. 과거 성능 수치는 섞지 않는다. 이전의 메모리 개선 전 워클릿은 이번 비교에서 제외하고 직전 개선 버전을 기준으로 삼았다.

## 바꾼 부분과 대조군

무거운 셀에는 제목·본문·합계·이미지와 64개의 둥근 색상 칸이 있다. 후보는 **장식 64칸만 하나의 네이티브 뷰로 그린다.** 데이터 10만 건, 문자열, 이미지, 합계용 4,000회 제곱근 계산, 풀 14개, 화면 밖 준비 목표 5행은 유지한다. 풀의 장식용 애니메이션 구독은 896개에서 14개가 된다. 실제 그리는 칸 수는 그대로다.

Android는 Canvas, iOS는 UIView의 drawRect에서 장식을 그린다. GPU API 설정을 바꾸지 않았다. iOS drawRect는 CPU 그리기 비용과 합성용 버퍼 비용이 생길 수 있으므로 GPU 가속 자체를 이번 개선 원인으로 주장하지 않는다.

**같은 장식 통합을 일반 FlatList에도 적용한 대조군**을 넣었다. FlatList 대조군은 원래의 React 셀·JS 렌더 경로를 사용한다. 이 대조군도 빨라진다면 해당 부분은 리스트 알고리즘 독점 이점이 아니라 셀 구조 단순화의 효과다. 다른 라이브러리에 동일한 장식 통합을 적용했을 때의 최적 성능은 측정하지 않았다.

워클릿의 10만 건 UI 데이터 사본과 최초 JSON 전달은 그대로 남는다. 동적 데이터 페이징·문자열 중복 제거·버퍼 축소를 함께 적용한 실험이 아니다. 고정 템플릿의 장식 전용 뷰는 임의 React 자식이나 개별 칸의 터치·접근성 요소를 대체하는 공개 API가 아니다. 예제의 전체 너비·고정 높이 행에 맞춘 PoC다.

## 환경과 준비량

- RN 0.87.1, FlashList 2.3.1, LegendList 2.0.19, Reanimated 4.6.0, Worklets 0.12.1.
- Android 16 API 36 arm64 에뮬레이터, iOS 26.2 iPhone 17 Pro 시뮬레이터. 소스 `864b6e6`, 두 플랫폼 arm64 Release를 새로 빌드했다. [소스·바이너리 해시](provenance.json).
- 전체 엔진을 포함하는 공통 앱이다. 각 라이브러리의 최소 제품 번들 비교가 아니다.
- FlatList·ZeroList에는 getItemLayout과 첫 화면을 채우는 initialNumToRender, FlashList에는 drawDistance, LegendList에는 고정 크기 힌트·재활용, ZigPool·워클릿에는 고정 풀을 사용한다. 구체적인 API 변환은 [직전 조건 문서](../2026-09-06-all-lists/methodology-ko.md)를 따른다.
- 준비 목표는 한쪽 5행이지만 실제 생성하는 뷰 수는 다르다. 특히 FlatList의 첫 행 구조와 풀 전체를 먼저 만드는 워클릿의 시작 비용은 다르다. 첫 확인 시 실제 붙은 행 수를 함께 보고한다.

## 측정과 정확성

엔진·플랫폼·조건별 3회씩, 시작 48회·평상시 비용 48회·JS 점유 비용 48회·JS 점유 화면 검사 48회로 **정식 192회**다. 시작 준비 실행 16회는 따로 보존하고 통계에서 제외한다. 구현 직후 4종을 1회씩 확인한 예비 시작 실행도 정식 결과에 섞지 않는다.

정식 비교 후 Android JS 점유 지연 증가를 확인하여 두 워클릿만 시드 870309로 3회씩 추가 비교했다. 이 6회는 정식 평균에 합치지 않았다. [추가 지연 검사와 최근 프레임 기록 분석](followup-ko.md).

시작은 네이티브 진입부터 현재 화면의 실제 제목·배치가 맞고 공백·겹침이 2px 이하인 첫 관측까지다. Android 기준은 SoloActivity onCreate, iOS는 AppDelegate didFinishLaunching 진입이다. OS 프로세스 생성 이전을 포함한 앱 전체 시작이나 실제 패널 표시 시간은 아니다. 워클릿 전체 UI 데이터 준비 시간은 별도 보조 지표다.

스크롤은 준비 스와이프 12회와 정량 스와이프 18회다. JS 점유는 160ms 작업과 40ms 여유를 반복한다. 순서를 난수 시드로 섞고 한 번에 한 플랫폼만 실행하며 측정 중 빌드·녹화는 하지 않는다. 각 플랫폼 안에서 입력을 같게 했지만 이동 거리와 두 플랫폼의 감속 물리는 같지 않다. 실행별 이동 행 수를 보존한다.

공백·내용·겹침 검사는 실제 네이티브 제목과 좌표를 읽는다. 비용 검사는 이 검사를 끈 별도 실행이다. 본문·합계·색상의 모든 프레임을 검사한 것은 아니다.

성능 측정과 별도로 두 플랫폼에서 4종의 초기·스크롤 후 화면 16장을 캡처했다. 초기 화면은 기존/통합 FlatList와 기존/통합 워클릿 각각 64칸의 중심 위치·색을 비교한다. 추가로 통합 워클릿의 스크롤 후 실제 제목 #3·#4·#5를 확인하고 384칸의 중심색을 해당 데이터의 기대 색과 비교한다. 모서리 안티앨리어싱 전체의 픽셀 동일성이나 모든 위치의 색 동기화를 보증하지 않는다. [초기 비교](pixel-validation.json), [스크롤 후 색 검사](recycled-color-validation.json).

## 해석의 경계

Android 메모리는 PSS, iOS는 RSS이며 서로 직접 비교하지 않는다. CPU는 한 코어 100% 기준 앱 프로세스 평균 사용량으로, 행당 비용이나 최대 처리량이 아니다. Android 지연은 gfxinfo 프레임, iOS는 CADisplayLink 콜백이라 같은 패널 누락 지표가 아니다.

외부 호스트 작업을 통제하지 못했다. 실행 전후 부하·프로세스 이름을 보존하고 느린 실행을 제외하지 않는다. 각 3회의 평균·중앙값·범위를 함께 읽어야 한다. 고정 높이의 이 화면에서 얻은 결과를 동적 높이, 임의 React 셀, 실물 구형 태블릿, 전력·발열, 장시간 누수까지 일반화하지 않는다.
